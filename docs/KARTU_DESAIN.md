# Kartu Desain

Dokumen ini memuat lima keputusan desain arsitektur penting dalam perancangan dan perbaikan ekstraktor CRUD SQL berbasis AST, termasuk pendekatan alternatif yang dipertimbangkan dan ditolak serta alasan teknis di baliknya.

| No | Keputusan | Alternatif yang ditolak | Alasan |
| --- | --- | --- | --- |
| 1 | **Presedensi Operator Logika `AND` dan `OR` Dinyatakan Berjenjang di Parser**<br>Di `crud/parser.py`, evaluasi ekspresi logika kami pisahkan ke dalam fungsi berjenjang sesuai aturan tata bahasa: `_logical()` menangani `OR` (presedensi terendah), lalu memanggil `_and()` untuk menangani `AND`, memanggil `_not()` untuk `NOT`, hingga turun ke operator pembanding (`_comparison()`). | Menyatukan evaluasi operator logika ke dalam satu fungsi tunggal memakai perulangan biasa dari kiri ke kanan (*flat loop*) atau tabel angka prioritas *ad-hoc*. | Struktur berjenjang ini adalah pola baku pada *recursive descent parser* (*Crafting Interpreters* Bab 6.2). Menggunakan tabel angka prioritas membuat kode tidak seragam dengan fungsi parser lainnya, sedangkan perulangan biasa dari kiri ke kanan akan keliru mengevaluasi `a OR b AND c` menjadi `(a OR b) AND c` (seharusnya `AND` dihitung lebih dulu). Lewat antrean pemanggilan fungsi (*call stack*), urutan prioritas dan pengelompokan dari kiri otomatis terjamin tanpa butuh variabel pelacak tambahan. Selain itu, klausa `BETWEEN a AND b` tetap aman karena token `AND` di dalam perbandingan dikonsumsi lebih dulu di tingkat `_comparison()` dan tidak bentrok dengan `AND` logika. |
| 2 | **Panic Mode Error Recovery Berhenti Tepat di Tanda Titik Koma (`;`)**<br>Pada fungsi `_synchronize()` di `crud/parser.py`, saat terjadi `ParseError`, parser membuang sisa token sampai menemukan tanda titik koma (`;`), lalu kembali ke loop utama `parse_script()` untuk memproses statement berikutnya. | Memotong token saat menemukan kata kunci awal statement baru (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) seperti pola umum di buku *Crafting Interpreters* Bab 6.3.3, atau langsung menghentikan pembacaan seluruh file sampai `EOF`. | Jika berhenti di `EOF`, satu saja query yang salah sintaks (seperti di file `campuran_error.sql`) akan menggugurkan seluruh query valid lainnya di file tersebut. Di SQL, kata kunci seperti `SELECT` sangat sering muncul di tengah-tengah query sebagai subquery (misal pada klausul `WHERE col IN (SELECT ...)` atau `FROM (SELECT ...)`). Jika parser berhenti pada kata `SELECT`, parser bisa keliru mengira subquery di dalam statement yang rusak sebagai statement baru yang mandiri, sehingga memicu rentetan error palsu berikutnya. Titik koma (`;`) adalah pembatas antar-statement yang paling definitif di SQL dan sesuai ketentuan `SPESIFIKASI.md` Bagian 6. |
| 3 | **Pencarian Scope Bertingkat dari Dalam ke Luar (*Lexical Scope Chain*)**<br>Pada `_lookup()` di `crud/resolver.py`, subquery membuat objek `Scope` baru yang menunjuk ke scope induknya (`scope.parent`). Resolusi alias tabel selalu memeriksa scope lokal terlebih dahulu, lalu menaiki rantai *parent* ke atas hingga ditemukan. | 1. Mengisolasi scope subquery secara penuh tanpa pointer ke *parent* (*isolated scope*), atau<br>2. Menyatukan seluruh alias dari semua level query ke dalam satu kamus simbol datar (*flat global dictionary*) per statement. | **Terhadap Correlated Subquery:** Jika memakai *isolated scope*, subquery tidak bisa membaca alias milik query luar sama sekali. Query berkorelasi seperti `WHERE p.id = o.pelanggan_id` akan gagal di-resolve karena alias luar `p` dianggap tidak terdefinisi.<br><br>**Terhadap Shadowing:** Jika memakai *flat global dictionary*, konsep *shadowing* akan rusak: saat subquery mendefinisikan alias `p` yang kebetulan sama dengan alias di query luar, keduanya akan bertabrakan atau saling menimpa secara global.<br><br>Pendekatan rantai leksikal dari dalam ke luar menyelesaikan kedua masalah tersebut (*Crafting Interpreters* Bab 11.3): *shadowing* otomatis terjamin karena scope lokal diperiksa lebih dulu, dan *correlated subquery* tetap didukung karena resolver otomatis mencari ke scope luar jika alias tidak ditemukan di lokal. |
| 4 | **Resolusi Kolom Tanpa Qualifier Dibatasi Hanya pada Scope Terdalam**<br>Pada fungsi `_column()` di `crud/resolver.py`, kolom tanpa nama tabel (misal: `WHERE status = 1`) hanya dicocokkan ke tabel yang terdaftar pada scope terdalam: tepat 1 tabel di-resolve ke tabel itu, $\ge 2$ tabel menghasilkan *warning* ambigu tanpa skema (`resolved = None`), dan 0 tabel menghasilkan *warning*. | Melakukan pencarian bertingkat ke scope luar (*outer scopes*) jika tidak ditemukan di dalam, atau menerapkan heuristik tebakan (*greedy guess*) dengan otomatis mengaitkan kolom ke tabel pertama pada klausa `JOIN`. | Ekstraktor ini bekerja secara statis tanpa koneksi ke database fisik (*schemaless*), sehingga sistem tidak memiliki katalog kolom fisik untuk tiap tabel. Jika pada query `JOIN` sistem sembarangan menebak tabel pertama atau mencari ke scope luar, data CRUD yang diekstrak berisiko tinggi mencatat relasi data palsu (*false positive*). Membatasi pengecekan hanya pada scope terdalam dan memberi *warning* saat ada multi-tabel adalah pilihan paling aman sesuai `SPESIFIKASI.md` Bagian 4.3.<br><br>**Kelemahannya:** Pada query yang sah dengan klausul `JOIN` di mana kolom tidak diberi qualifier (misalnya `SELECT nama, total FROM pelanggan JOIN pesanan`), resolver terpaksa membiarkan `resolved = None` (tidak dapat di-resolve) dan memunculkan *warning* ambigu, meskipun pengguna tahu kolom tersebut hanya ada di salah satu tabel. Namun, *trade-off* ini sengaja diambil demi mencegah pencatatan relasi CRUD palsu. |
| 5 | **Penyatuan Representasi `INSERT ... SELECT` dengan Dukungan Subquery Bertanda Kurung**<br>Pada `_insert()` di `crud/parser.py`, parser menyatukan penanganan klausa `VALUES` dan query `SELECT` pada node AST `ast.Insert` tunggal dengan dukungan kurung simetris: parser memeriksa lookahead `_next_is_select()`, mengonsumsi kurung pembuka `(` sebelum `_select()` dan menuntut `)` penutup setelahnya, lalu analyzer secara otomatis menandai tabel target sebagai Create (`C`) dan seluruh tabel di subquery sebagai Read (`R`). | Membuat kelas AST dan fungsi parser/resolver terpisah (`ast.InsertSelect`), atau membatasi gramatika hanya mendukung format lurus tanpa kurung (`INSERT INTO t SELECT ...`) dan menolak bentuk bertanda kurung sebagai error sintaks. | Membuat kelas AST terpisah akan memicu duplikasi kode yang tidak perlu, karena cara membaca tabel tujuan dan daftar kolom pada kedua jenis query tersebut sama persis. Dengan menyatukannya pada satu kelas `ast.Insert`, fungsi analyzer cukup memeriksa apakah ada subquery (`if stmt.query: ...`) secara otomatis. Selain itu, menolak subquery bertanda kurung akan membuat parser gagal membaca query valid yang lazim ditemui dalam SQL riil (seperti di sampel data audit). Penggunaan lookahead `_next_is_select()` menjamin kata kunci `SELECT` tidak salah dikira sebagai nama kolom tujuan di dalam daftar kolom `(col1, col2)`. |
